# Dagyard v0 — spec de la corrida nocturna (2026-10-04)

> **Fuente de la intención:** el documento de intención del panel (privado, fuera de este repo; §1 verbatim
> manda; §5 tiene las decisiones D1-D11). Si este spec contradice §1, gana §1.
> Encargo: el proyecto terminado en una noche, revisado la mañana del 2026-10-04.

## Qué es, en una línea

El lugar donde un PM ve el plan de su fábrica de agentes como un **DAG vivo en 3D**, sabe en qué etapa
va el proyecto, recibe solo lo que le toca (**decisiones, revisiones y accesos**), desbloquea desde ahí,
y lee lo que los agentes le escriben en corto, con los informes de Basalt colgados de cada tarea.

## Lo que André tiene que poder hacer mañana (definición de terminado)

1. Abrir una URL hospedada (workers.dev sirve; el dominio todavía no se compra) y entrar con un token.
2. Ver el **proyecto de ejemplo «Marketplace de reservas»** con la estética del preview
   (`dagyard-design/design/preview-constelacion.html`): constelación 3D, travellings de cámara, vista general que entra
   en cuadro, ficha del nodo y carril de etapas. **Mismo nivel de pulido o mejor.**
3. Resolver los tres bloqueantes desde la UI (una decisión, una revisión y un acceso) y ver que el estado
   **persiste** (recargar la página no lo pierde, porque vive en el servidor).
4. Ver cambios **en tiempo real** sin recargar: correr en una terminal un comando del CLI (por ejemplo
   `dagyard msg …` o `dagyard done …`) y verlo aparecer en el navegador en ≤3 s.
5. Ver un **segundo proyecto real**: el DAG de una corrida de la fábrica importado desde `.cofoundy/tasks`
   (`dagyard import`), para comprobar que no es solo una demo.
6. Leer un `/reporte-po` en Basalt con capturas debajo de cada feature, más un handoff que diga qué falta.

## Público y lenguaje (D10, no negociable)

Para PMs, no para devs. Nada de `T-402`, nombres de archivo ni jerga en la UI. Los entregables llevan
nombre humano. Etapas: Descubrimiento → Diseño → Construcción → Pruebas → Lanzamiento (o las que defina
el proyecto). Estados: Done · In progress · Needs you · Pending (en español: Lista, En progreso, Te espera,
Pendiente). **Idioma (pivot de D10, Mensaje 8 del 2026-10-04, #73):** inglés por defecto; español si el
sistema del usuario está en español (web: `navigator.languages`, con un selector que se recuerda; CLI y
mod: `LC_ALL` > `LC_MESSAGES` > `LANG`). El español va con tildes y tuteo, nunca voseo. Lo que escribe un
usuario (títulos, mensajes de agentes, nombres de etapa) no se traduce. Estética (D8): sencillísima, futurista y muy vistosa, con poco que hacer. El grafo es la pantalla.
Anti-referencias: `dagyard-design/design/2026-10-03-anti-ref-*.png` (ni dashboard de KPIs, ni sidebar, ni kanban).

## Arquitectura (decidida; un sitio puede cambiarla solo si escribe por qué)

- **Hosting: Cloudflare** (el mismo stack que `products/basalt`; ese repo sirve de receta: `wrangler.toml`
  y deploy). `CLOUDFLARE_API_TOKEN` está en el env (medido 2026-10-04: `wrangler whoami` responde
  con la cuenta). No hay token de Supabase ni de Vercel; no los uses.
- **SSOT = el servidor** (D2): un Worker guarda proyectos, etapas, nodos, dependencias, bloqueantes,
  mensajes y eventos en el Durable Object `Store`, uno solo para todos los proyectos y con SQLite.
  `.cofoundy/` es solo una fuente de importación.
- **Dónde viven los datos (decidido el 2026-10-13, #9): se quedan en el `Store`, no se migra a D1.**
  El `Store` ya es una sola base SQL para todos los proyectos, así que las consultas entre proyectos
  (la única razón de #9 para migrar) ya se pueden hacer ahí. Además, el token de Cloudflare no tiene
  permiso de D1 (medido el 2026-10-13: código 10000). Se reabre si el `Store` se vuelve el cuello de
  botella de escritura, si se acerca al límite de almacenamiento de un Durable Object, o si hace falta
  una consola SQL fuera del Worker.
- **Tiempo real:** un Durable Object por proyecto con WebSocket (o SSE). Cada escritura emite un evento
  y la UI lo aplica sin recargar.
- **Frontend:** Vite + React + three.js (puede ser react-three-fiber o three directo), servido por el
  mismo Worker como assets estáticos. Puerta del preview: reutiliza su escena, texturas y cámara.
- **Auth v0:** un solo dueño. Token de dueño (para la UI) y API key (para agentes), ambos como secrets del
  Worker. Guarda el token de dueño en `~/.config/dagyard/owner-token` (chmod 600) y di dónde está en el
  handoff. **Nunca** lo pegues en Basalt, en un issue ni en un commit.

## Modelo de datos mínimo

- `project`: id, nombre, etapas ordenadas.
- `node`: id, proyecto, etapa, título humano, estado (`pending|working|blocked|done`), progreso 0-1,
  equipo/agente, `goal` (la misión de una línea que se le inyecta al agente como `/goal`, D-goal por
  nodo), `report_url` opcional.
- `edge`: from → to (dependencia).
- `blocker`: nodo, tipo (`decision|review|access`), pregunta, opciones, resolución, quién y cuándo.
- `message`: nodo, de quién, texto ≤280 caracteres, `report_url` opcional. Concisión por diseño (D6).
- `event`: log append-only de todo lo anterior, porque de ahí sale el tiempo real.

## Interfaz para agentes (lo que usa `/factory`)

Un CLI `dagyard` (Node, sin dependencias pesadas) sobre la API REST:

- `dagyard node add|update|start|progress|done` y `dagyard edge add` → el DAG muta (D5: los sitios
  agregan; factory reordena, parte o borra; el humano aprueba solo lo que toca el alcance, que en v0 se
  marca como un bloqueante `decision`).
- `dagyard block <nodo> --kind decision|review|access --q "…" [--opt …]` y `dagyard wait <nodo>`
  (bloquea hasta que el humano resuelve y devuelve la resolución).
- `dagyard msg <nodo> "…" [--report <url>]`.
- `dagyard next --project <p>` → el siguiente nodo arrancable **con su línea de `/goal` lista para pegar**:
  un goal por nodo, que es como la fábrica inyecta las misiones.
- `dagyard import --from <ruta a .cofoundy/tasks>` → crea un proyecto desde las tareas del orchestrator
  (`blockedBy` → aristas, `status` → estado).

**Stretch, solo si lo anterior está verde:** un *channel* de Claude Code (MCP con capability
`claude/channel`, ver https://code.claude.com/docs/en/channels-reference) que empuja la resolución de un
bloqueante a la sesión del agente y expone una tool `reply` con campos cortos. Research preview: se carga
con `--dangerously-load-development-channels`. Si no entra, queda como issue para v1.

## Gates (cada sitio los corre antes de decir «listo»)

- `pnpm typecheck`, `pnpm test` (vitest: API, modelo y CLI) y `pnpm build`, leídos por su exit code.
- Deploy a workers.dev y **sonda de efecto**: la URL sirve el build nuevo y la API responde con el token.
- Captura con navegador real (agent-browser) de la vista general, la ficha y un bloqueante resuelto; las
  capturas van al reporte.
- Prueba de tiempo real: un comando del CLI aparece en la UI abierta en ≤3 s (medido, no supuesto).

## Fuera de alcance en v0

Multi-tenant, cobros, Casdoor, comprar el dominio, móvil pulido (que funcione basta) y hacer público el
repo (quedaba privado hasta que el dueño lo aprobara; después es OSS, D1. Se aprobó el 2026-10-04, #25).

## Entrega de la mañana

- URL + dónde está el token.
- `/reporte-po` en Basalt (capturas debajo de cada feature, lo decidido y lo pendiente).
- Handoff (vive con el informe, fuera del repo) e issues `agent-ready` para lo que falte.
